# 결정 기록

작성자: 문규남. 각 결정은 막힌 지점, 고른 방법, 근거 순서로 남긴다.

## D1. 실습 환경은 수업 서버가 아닌 클라우드 작업공간으로 한다
- 막힌 지점: 수업 서버 SSH 접속에는 개인 키 파일과 VS Code가 필요하다.
- 결정: 앱 제작·Git·수집기 실습은 클라우드 작업공간에서 하고, 서버 접속·확장 설치·로그인 3개는 직접 한다.
- 근거: 키 파일은 남에게 넘기지 않는다는 수업 원칙을 지킨다. 실습 결과(코드, PR, 수집 결과)는 환경과 무관하게 같다.

## D2. 포트는 3099를 쓴다
- 근거: 수업 예시 포트다. 수업 서버에서는 배정 포트 30NN으로 바꾼다.

## D3. GitHub이 정본, 로컬 Git은 빌드·검증용이다
- 막힌 지점: 클라우드 작업공간의 gh 토큰이 유효하지 않아 git push를 할 수 없다. 연결된 GitHub 도구는 파일 단위 commit, 브랜치, PR, Issue, merge만 지원한다.
- 결정: 코드는 로컬에서 만들고 검증한 뒤 GitHub 도구로 commit한다. 로컬 commit 해시와 GitHub commit 해시는 다르다.
- 근거: 수업이 요구한 결과물(PR merged, Issue Closed)은 GitHub 화면에 남아야 한다.

## D4. 작성자는 본인 한 명이다
- 결정: commit 작성자는 본인 계정이며 Co-Authored-By에 Claude를 넣지 않는다.
- 작성 방식: 본인의 아이디어를 Claude로 템플릿화해 초안을 잡고, 직접 검토하며 구체화했다.

## D5. 실습 B·C는 브라우저로 받은 원문을 쓴다
- 막힌 지점: 작업 환경 네트워크 정책이 두 사이트를 막았다. 수업 자료의 보관 사본도 드라이브에 없다.
- 결정: 본인 PC의 브라우저에서 원문을 받아 옮긴다. 큰 원문을 통째로 옮기면 손상될 수 있어(B 2·3페이지 CRC 오류), 브라우저에서 원문 SHA-256과 바이트 수를 기록하고 표의 행(tr.team)만 옮긴다.
- 근거: 원문을 받았다는 사실과 원문 동일성(해시)은 남기고, 분석에 필요한 행은 손실 없이 옮긴다. source_kind는 actual(브라우저 경유)로 적는다.

## D6. 충돌 해결의 마지막 단계는 본인이 GitHub 웹에서 한다
- 막힌 지점: 연결된 GitHub 도구는 부모가 2개인 merge commit을 만들 수 없다.
- 결정: 충돌 PR(title-b)까지 만든 뒤, 본인이 PR 화면의 Resolve conflicts로 남길 쪽을 고르고 merge한다.
- 근거: 수업과 같은 진짜 merge commit을 남긴다. 어느 쪽을 남길지는 사람이 정한다는 수업 원칙과도 맞다.

## D7. PRD 주제는 AX 아이디어 보드로 한다
- 근거: 실행되는 앱과 PRD·구조도·와이어프레임·수락조건을 바로 대조할 수 있다. 확인하지 않은 내용은 [가설]로 표시한다.

## D8. 처음 선택(decision_record)은 본인이 직접 채운다
- 근거: 자료를 보기 전 판단은 본인 경험에서 나와야 한다. 그 칸은 비워 두고 자료 판단 부분만 작성한다.

## D9. 자기 PR 리뷰는 Comment로 제출한다
- 막힌 지점: GitHub은 작성자 본인의 PR에 Approve를 허용하지 않는다.
- 결정: Submit review는 Comment로 하고, 확인 항목(파일·동작·보존)을 리뷰 본문에 적는다.

## D10. 10/10 작은 변경은 B(제목 안내 문구)로 한다
- 근거: 수업 규칙은 삭제 확인이 없으면 A, 이미 있으면 B다. 3주차 Issue 실습에서 삭제 확인창을 먼저 넣으므로 B를 고른다.

## D11. 4주차 수집기 코드는 같은 저장소의 practice/ 폴더에 둔다
- 근거: 실습 결과를 한 저장소에서 찾을 수 있다. 올리는 범위는 D17을 따른다.

## D12. GitHub 쓰기 권한 확보 방법을 본인에게 묻는다
- 막힌 지점: 연결된 토큰은 fine-grained 토큰으로 보이며, 새로 만든 ax-board-practice에 접근 권한이 없다.
- 선택지: (1) 토큰의 Repository access에 ax-board-practice를 추가한다. (2) 본인 PC의 git 인증으로 push한다.
- 근거: 토큰·인증 설정 변경은 계정 보안 설정이라 본인이 직접 해야 한다.

## D13. GitHub MCP는 앱을 다시 시작해 새 토큰을 읽게 한다
- 막힌 지점: 설정 파일의 토큰은 19:52에 바뀌었지만 실행 중인 MCP 프로세스는 그 전에 시작됐다.
- 결정: Claude 데스크톱 앱을 완전히 종료한 뒤 다시 연다. 토큰을 스크립트로 직접 꺼내 쓰지 않는다.
- 근거: 토큰 값을 작업 기록이나 명령에 노출하지 않는다. 앱이 MCP를 다시 띄우면 같은 설정으로 쓰기가 된다.
- 참고: 저장소가 Public으로 만들어졌다. 공개 여부는 본인이 정한다.

## D14. 토큰의 저장소 범위를 본인이 수정한다
- 막힌 지점: 재시작 후에도 쓰기가 실패했다. fine-grained 토큰이 선택한 저장소에만 쓰기를 허용하고, ax-board-practice가 그 목록에 없는 것으로 판단한다.
- 결정: 본인이 토큰 설정에서 Repository access에 ax-board-practice를 넣고 Contents·Pull requests·Issues를 Read and write로 바꾼다. 같은 토큰 값이 유지되므로 앱 재시작은 필요 없다.

## D15. package-lock.json은 GitHub에 올리지 않는다
- 막힌 지점: 연결된 GitHub 도구는 파일 내용을 그대로 실어 commit하므로 165KB 잠금 파일을 옮기기 어렵다.
- 결정: 잠금 파일은 빼고 올린다. `npm install`이 다시 만든다.
- 영향: 설치 시점에 따라 의존성 세부 버전이 달라질 수 있다.

## D16. 3주차 기능은 로컬에서 먼저 구현·검증한 뒤 같은 순서로 GitHub에 올린다
- 근거: 토큰 수정을 기다리는 동안 작업을 멈추지 않는다. 브랜치별 결과(검증 통과, build 성공)를 미리 확인해 두면 GitHub에서는 PR·merge만 하면 된다.

## D17. GitHub 반영 순서와 범위
- 순서: ① main 기본 기능 → ② 태그 필터 → ③ feat/title-change PR → ④ Issue·삭제 확인창 PR → ⑤ README PR → ⑥ Issue·아이디어 개수 PR → ⑦ CLAUDE.md Git 규칙 PR → ⑧ 10/10 PRD 문서·작은 변경 PR·리뷰·handoff branch → ⑨ 충돌 PR(title-a merge, title-b 충돌)
- 근거: 아이디어 개수 기능은 제목 줄(h1)을 고친다. 충돌 PR을 먼저 열면 이후 PR까지 충돌이 이어지므로 충돌 실습을 맨 뒤로 옮긴다. 수업 순서와 다르지만 확인하는 결과는 같다.
- 4주차 실습은 practice/ 폴더에 코드·계획·확인 기록만 올린다. 원문 CSV·HTML과 runs/ 결과는 용량 때문에 올리지 않고, 스크립트로 다시 만든다(실습 A). 실습 B·C는 브라우저로 받은 행 값(relay)을 함께 올린다.

## D18. 올린 파일은 git blob 해시로 대조한다
- 막힌 지점: 연결된 GitHub 도구는 파일 내용을 그대로 실어 보내므로 옮기는 과정에서 글자가 바뀔 수 있다(실습 B 2·3페이지에서 실제로 손상이 났다).
- 결정: 올린 뒤 GitHub의 파일 해시와 로컬 `git hash-object` 값을 비교한다. 저장소가 Public이라 clone해서 확인할 수도 있다.
- 결과: 올린 파일은 로컬 검증본과 같았다. 이 decisions.md를 처음 올렸을 때 1글자 차이(바뀔→바뀌)를 이 대조로 찾아 같은 PR에서 고쳤다.

## D19. 자기 PR의 수정 요청은 Comment 리뷰와 같은 PR의 수정 commit으로 남긴다
- 근거: 작성자 본인은 Request changes를 제출할 수 없다(D9). 리뷰 본문에 "수정 요청 1건"을 적고 같은 branch에 수정 commit을 이어 수업의 "같은 PR 수정" 흐름을 남긴다(PR #8).

## D20. merge가 끝난 원격 브랜치는 남겨 둔다
- 막힌 지점: 연결된 GitHub 도구에 브랜치 삭제 기능이 없다.
- 결정: Delete branch는 본인이 PR 화면에서 누른다. 기록 보존이 필요한 handoff 브랜치는 지우지 않는다.
